# Forgia 模组并行 API 设计草案

状态：RFC。第一阶段已部分实现，具体边界见下方实现指南；本文其余新增类型、方法和协议仍为设计示意，不能直接作为当前 API 使用。

目标：让模组作者通过公开接口适配 Forgia，不依赖 RegionThreadingEngine、ThreadLocal 或内部 patch；以 MobSpawnController 的自然刷怪结构过滤为第一个验证案例。首先设计协议并验证接入点，再冻结 API。

第一阶段已落地的接口和接入示例见 [实现指南](MOD-PARALLEL-API.md)：目前只有服务器级注册、执行阶段和 per-chunk 刷怪准备协议。本文中的纯过滤器、结构数据服务、监听器接管、独立 Maven 发布和整批规则快照仍是后续设计，不属于当前能力。

## 1. 设计边界

- 核心提供调度、所有权、执行阶段、任务生命周期和受控的数据准备机制。
- 模组负责自己规则、缓存、监听器和回调的并发正确性。
- API 不能自动恢复任意 Java 调用栈，也不能撤销已产生的副作用。
- 读取到实体或区块引用不代表获得修改权限；在主线程运行也不必然代表全世界静止。
- 支持并行是按“模组功能 + 执行阶段”注册，不使用一个 `threadSafe=true` 放行整个模组。
- 性能退化和行为退化分别报告；不把未知数据当作空世界、不把未执行的回调当作成功。

## 2. 现有接口复用与缺口

| 现有入口 | 继续复用 | 需要补充 |
|---|---|---|
| `RegionThreading` / `RegionThreadingManager` | 调度入口与所有权断言 | 能力查询、显式执行阶段、服务发现 |
| `RegionScheduler` / `EntityRegionScheduler` / `GlobalRegionScheduler` | 按位置、实体、全局状态安排任务 | 逐项审计生命周期与未安装引擎时的语义；不能直接承诺现有实现具备新增协议 |
| `EntityInteractionScheduler` | 整体交互、owner 操作、加载后执行 | 保留 Experimental，复用结果状态，不另造相同功能的调度器 |
| `RegionThreadingDeclarations` | 管理员收窄策略、模组资源声明 | 统一注册来源、版本要求、冲突优先级；区分声明与实际激活 |
| `RegionThreadingConflicts` / compat report | 已知风险与收窄执行范围 | 显式适配器接管协议，不能仅看到适配器 jar 就取消保护 |
| `RegionSpawnPlan.accept/executeAndAwait` | 已有准入与并行批次 | 准备完成后、任何本批次刷怪副作用开始前的统一准入点 |

内部 `region` 包、Engine、Hooks、lease 对象、batch 对象和可变诊断记录不构成稳定公共 API。

## 3. 发布与加载

建议新增公共门面包 `net.neoforged.neoforge.server.threading.api`，不立即迁移现有包；通过桥接复用现有调度器。

第一阶段随 Forgia 发布编译用 API artifact（建议坐标 `net.forgia:forgia-api`，最终坐标待发布基础设施确认）。运行实现由核心提供，模组不得把第二份 API 打包进 jar。

提供两种接入：

1. 原生 Forgia 模组：依赖 API，由 Forgia 注册事件获取注册器。
2. 同时支持原版 NeoForge 的模组：用独立适配模组，或在确认 Forgia 存在后才加载专用入口类；普通入口和类签名不得直接引用可选 API。具体 metadata/entrypoint 格式在实现加载器前不冻结。

API 有独立主版本和能力标识。主版本不匹配时拒绝激活适配器并给出原因；缺少可选能力时保留串行路径。调用方按能力查询，不比较 `.43/.44` 这样的核心构建字符串。

服务生命周期绑定服务器实例；一个 JVM 内第二次启服不能复用第一次的注册、任务或世界引用。引擎关闭时提供明确的串行模式能力，不能静默把任务送入公共异步线程池。

## 4. 模组注册与策略

拟议注册入口：`RegisterParallelAdaptersEvent`，服务器启动期间在主线程调用，注册完成后冻结。它发生在 mod、注册表和配置就绪之后，首次世界 tick 之前。

每个适配器注册：

- 唯一 `ResourceLocation`，例如 `mobspawncontroller:natural_structure_filter`。
- 实现所属模组、被适配模组及支持的 API 主版本。
- 明确的功能范围，例如 `NATURAL_SPAWN_FILTER`，而非整个 `SPAWN` 事件总线。
- 所需能力、数据依赖、串行路径与诊断说明。
- 接管的原监听器/判断路径，以及验证接管完成的方法。

注册顺序不决定规则优先级。重复 id、两个适配器接管同一路径、缺失依赖或无法确认原路径已被接管，均激活失败并保留串行路径。失效时不能留下“原监听器已卸载但替代逻辑未就绪”的半安装状态。

有效策略由以下因素共同决定：管理员收窄配置、核心不变量、模组风险表、已成功激活的具体适配器。适配器只能解除其明确覆盖的那条风险；管理员强制串行不能被适配器覆盖。现有 harness force 开关不等于生产支持承诺。

## 5. 执行上下文与所有权

公开只读 `ExecutionContext`，至少区分：

| 阶段 | 可做的事 |
|---|---|
| `QUIESCENT_SERVER` | 在该阶段合同内执行世界操作；可运行串行回退及有预算的数据准备 |
| `REGION_WORKER` | 操作本次授权范围内的状态，读取已发布数据 |
| `SERVER_SERVICE` | 主线程为仍活跃的 worker 完成特定服务；仅执行服务合同允许的操作，不能随意加载或修改世界 |
| `EXTERNAL` | 网络线程、异步计算线程等；无世界访问权限 |

上下文暴露阶段、服务的服务器实例、可选维度与批次标识，不暴露可续期的 lease。缓存一个 context 对象不能延长权限。

保留位置/实体所有权查询，但新增按操作语义的检查，例如实体变更、已加载区块读取。`isOwned` 不能被解释为支持加载、跨维度传送或所有任意模组回调。

动态 region 编号不是稳定身份，不能作为模组缓存键。长期任务按世界身份与位置或实体身份路由，执行前重新解析 owner。

## 6. 数据准备与 worker 准入

提出通用的 `PreparedWorkAdapter<S>` 协议，先只给自然刷怪实现，避免为其他 slice 提前许诺相同语义。

生命周期：

```
收集本批次候选工作
  -> 主线程静止阶段准备数据 / 做无副作用准入检查
  -> 为每个单元确定 WORKER_READY 或 SERVER_REQUIRED
  -> 固定规则版本、准备结果与生命周期
  -> 按规定顺序执行 worker 单元及串行单元
  -> 汇合、原有实体准入与清理
```

`S` 不是任意可以长期缓存的 Object。推荐只包含 id、数值、不可变位置、规则及结构包围盒等脱离世界的值。Java 的 `record` 不自动保证深层不可变；公开合同禁止携带 live LevelChunk、Entity、BlockEntity、可变 NBT、随机数发生器或共享规则编辑器。

拟议准备结果是带类型的联合结果：

- `Ready<S>(snapshot, ruleRevision)`：数据完整，可在合同范围内运行。
- `ServerRequired(reason)`：开始 body 前选择原有串行路径。

运行期 provider 抛异常是 FAILED，不自动当成 `ServerRequired`；否则初始化 bug 会被隐藏。预期的缺数据、预算不足应显式返回 `ServerRequired`。

规则/数据的版本在批次内固定。reload 只影响之后的批次；旧版本由仍使用它的批次持有，结束后释放。快照过期、世界卸载、服务器关闭的批次不得继续提交效果。

准备阶段必须有工作量预算、缓存失效机制和内存上限。默认只读取已加载的所需数据；不能为每个候选位置同步加载整个邻域。如果无法准备，完整单元串行执行，不能把部分 worker 工作重新执行一遍。

单元建议为“本 tick 某 chunk 的完整自然刷怪调用”，而非 region 或某个已执行一半的事件回调。准入检查不得消费游戏 RNG、发事件、构造实体或修改 mob cap。

实施前必须调整 `RegionSpawnPlan`：当前 `accept()` 的部分拒绝会立即 `spawnInline`，不能简单在后面的 `executeAndAwait()` 加一个准备回调就声称整个批次有统一快照。需明确早期串行单元与准备时点、计数共享和原有事件顺序的合同，并用生产路径测试验证。

## 7. 自然刷怪适配协议（第一阶段）

提供专用 `NaturalSpawnFilter<S>` 扩展点，语义是“额外约束”，不能绕过 vanilla gate、事件取消和 mob cap。拟议接口形状如下，非当前可编译接口：

```java
interface NaturalSpawnFilter<S> {
    Preparation<S> prepare(SpawnPreparationContext context);
    SpawnDecision evaluate(SpawnCandidate candidate, S prepared);
}
```

- 准备 context 只提供合同内的数据访问器、工作范围、预算及规则版本；不提供任意可变 ServerLevel 作为通行证。
- candidate 是 entity type、候选位置、维度、生成原因等不可变值；不传活实体，不能查询它来间接修改世界。
- decision 为 `PASS` 或 `DENY`。`PASS` 仅代表此过滤器不拒绝，不代表最终允许生成。
- `evaluate` 中不能再返回串行回退要求：刷怪流程可能已有副作用。回退必须由 prepare 在 body 前决定。
- 多个纯过滤器按注册的稳定 id 顺序调用，任一 DENY 则拒绝；不宣称这能代替任意有副作用的 NeoForge 事件监听器。
- 事件仍按原有生命周期发布一次；事件分派不因适配器引入而重复，也不随便改变其他监听器相对顺序。

MobSpawnController 首次适配：准备其实际规则要求的结构起点/引用与有效包围盒；依据原实现选择 piece 或 whole-structure 语义，不能只判断候选 chunk 是否带结构名称。跨 chunk 结构引用、不存在与不可用必须区分。数据不完整就选择该单元串行执行。

原模组的 FinalizeSpawn 过滤必须有经过验证的入口，能对“适配器已处理的自然刷怪”跳过相同判断，同时保留其他生成原因的原实现。不能只以 `isWorkerThread` 判断已处理。若无法无副作用地抽取规则并保持原有判断时点，则第一阶段不激活，仍串行；需要与模组协作改扩展点，而非改变游戏规则来迁就 API。

本模组适配完成后，其他 FinalizeSpawn 监听器仍不自动安全。核心需要单独报告未覆盖的监听路径；v1 不提供“扫描所有监听器并证明线程安全”的承诺。

## 8. 跨所有权操作与结果

复用现有 interaction / owner-operation API：调用前提交整个操作，捕获不可变参数，执行时重验身份、维度与生命周期。已有 `submitToOwnerAfterChunkLoad` 是静止主线程上的有 ticket 同步加载，不应改名包装成异步加载能力。

新模块如需其他操作，以独立能力发布，不向模组暴露通用的“worker 内同步执行任意主线程 Runnable”接口。否则 API 会重现隐藏加载、跨线程阻塞和死锁问题。

所有新任务接口必须定义：接受与执行的区别、容量拒绝、取消边界、owner 失效、卸载、关闭、回调异常、引用释放，以及至少一次/至多一次。目标合同是至多一次执行，不是保证必达。worker 不得 `join/get` 等待其他 owner 或主线程任意任务完成。

## 9. 诊断与失败处理

`compat` 按 adapter id 显示：注册者、功能范围、版本、激活/串行/失效、所需能力及原因。`status` 只显示聚合计数；详情放在明确的子命令中。

计数至少包括：准备耗时与缓存命中、worker 单元、开始前串行单元及原因、生命周期跳过、容量拒绝、回调失败。计数单位明确区分候选、chunk 调用、实体和事件，不混为“刷怪数”。维度与类型等标签必须有上限，不能无限创建指标。

日志限频并保留首个完整原因；不要仅为消除 EventBus ERROR 而把未知结构当成不存在。EventBus 的异常传播与监听器后续执行必须通过实际版本验证，不预先假设其会吞掉异常并继续，也不让适配器依赖这一点。

现有 `.43` 实体 tick 截断是运行时保护，不是 v1 的成功执行或兼容认证。一个类可能有多个已提交实体并发失败，因此不能对 API 用户承诺“一类最多损失一次 tick”。API 正常路径应在 body 前保证准入。

## 10. 实施顺序与验收

1. 固定执行上下文、能力与注册/失效协议；审核既有调度器，建立 API 文档和开发用 artifact。
2. 重构自然刷怪准备/准入边界，确保任何 fallback 都发生在完整单元副作用开始前；原路径仍可独立运行。
3. 做 MobSpawnController 独立适配模组，复用或与上游协作暴露纯规则接口；旧监听器接管与替换必须一同成功。
4. 用第二个小型示例模组接入同一 API，证明公共接口不依赖 MobSpawnController 私有实现。
5. 完成行为和性能验证后，冻结 API v1。首次实现前只承诺 Experimental。

验收场景：

- 结构跨 chunk、起点在未加载 chunk、有引用但数据不完整、piece/整体包围盒、多个结构重叠。
- 同一候选固定规则下，对比原模组串行判断与适配判断，逐条一致；结构缺失与数据未知不能混淆。
- 原监听器只执行一次，DENY 不被后续 PASS 放行，其他模组事件取消及非自然生成保持原语义。
- 配置重载、chunk 卸载、维度关闭、服务器重启、适配器重复注册、接管失败和预算耗尽。
- 对比 vanilla/原模组串行、Forgia 串行、Forgia 适配并行三种模式；准备成本计入总刷怪耗时。
- mob cap、实际实体加入/取消、RNG 消耗边界与副作用次数验证；并行顺序导致的既有差异单独列出，不宣称逐 tick 全世界完全一致。
- 真实整合包多玩家长跑，至少覆盖此前 structure_starts 报错区域，记录吞吐、p95/p99、主线程成本、回退与异常，不能用仅启动成功证明兼容。

第一阶段不包含动态 region、跨区事务、自动字节码并发证明、任意 worker 同步加载、透明续跑或任意模组事件的并行化。
