# 线上崩溃前性能对比：2026-11-11

来源为面板只读下载的 `logs/tick-diagnostics/flight-*.txt` 与滚动游戏日志，原始副本、统计脚本和 JSON 在
`tmp/online-performance/`。没有发送服务器命令、修改配置或重启。时间均为日志原始 UTC；北京时间加 8 小时。

## 统计口径

诊断器只记录超过约 250ms 的 tick，不能据此计算平均 MSPT、TPS、全体 tick 的 p95/p99。
以 RECOVERED 为一次慢 tick，不把同一 tick 的多个 LIVE_STALL 栈重复计数。统一剔除启动前 10 分钟、
结束前 1 分钟（避免把崩溃报告生成/停服当作正常 tick）。版本从实际运行栈/启动日志确认。

用游戏日志 joined/left 事件重建在线区间，只统计有人在线区间的慢 tick，并除以“至少一个玩家在线的
墙钟时长”，不是玩家人时。诊断快照的玩家名单可能滞后，不能只按快照是否含 player 字段分类。
11 月 9 日两轮原版日志的上线记录未完整下载，不纳入主比较。当前原版轮次仍在运行，以下截至抓取报告
最后样本约 11-11 10:17 UTC；末尾一分钟同样排除。

## 崩溃前 .44 的卡顿位置

- 03:51:00：2.131s，server CPU 2.107s，GC 0。栈显示 DataFixerUpper / StructureTemplateManager /
  StructureStart / ChunkSerializer.unpackStructureStart / ChunkMap.scheduleChunkLoad，属于结构模板/区块加载
  数据转换路径。不是 GC 暂停，也不是根据栈顶 CHUNK_LOADING_OR_WAIT 标签就能断言 worker 屏障是唯一原因。
- 02:00:04–02:00:08：1.325s、1.203s、1.316s，栈涉及 Create Deployer、contraption NBT/实体同步包和
  Funnel/Deployer 主线程 block-entity fallback 的 codec/DataFixer 数据处理。
- 01:54:18：1.112s，DataFixerUpper 类型重写。
- 03:41–04:06 每隔约五分钟有 0.38–0.51s 事件，至少应再按实际栈检查保存/周期任务；不能只凭周期猜因。
- 04:10:47 崩溃是 Shulker.onPeekAmountChange -> Entity.move 外部实体写守卫失败。末尾报告生成包含长停顿，
  已排除出正常性能统计；稳定性失败单独保留，不因之前慢 tick 较少而忽略。

前一轮 .44 的 134.032 秒事件发生于 11-10 15:57:10，server CPU 11.151s、JVM GC 8.255s，样本落在
entity worker barrier 等待。它确实记录在报告里，不能将该轮描述为没有严重卡顿；但仅服务器线程采样不足以
判定剩余等待全部来源，需要 worker 栈/宿主调度证据。另有约 20.0s、16.6s 长 tick。

## 结论

崩溃前最新 .44 比其前一轮更少出现长卡顿，但低在线时间掩盖了总小时统计。按有人时间计算，它接近其中
一轮原版，未证明普遍更快。主要已观察到的主线程长任务仍是结构数据转换与 Create 相关的数据处理。
此外潜影贝导致停服的事实优先于“平均看起来更流畅”；修复已在本地后续构建中验证，不能误称线上已修复。
